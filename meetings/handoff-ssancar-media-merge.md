## 0. 한 줄 요약

`?vin=&car_no=` 교차매칭이 **매칭된 검차글 중 1건만** 돌려준다. 그런데 ssancar 검차 게시판은 **같은 차를 글 2개**(영상글 + 사진전용글)로 등재하고, 교차매칭이 잡는 쪽이 **사진전용글**이라 `videos:[]` 로 보인다. 그 결과 **영상이 분명히 있는데도 board 자동전달대기 전이가 안 된다.** → **매칭된 검차글 전부의 `videos`/`photos` 를 합산**해서 돌려달라.

---

## 1. 실측 (2026-07-28, heymanboard 박스에서 직접 호출)

같은 차가 wr_id 2개로 올라와 있다. `sale_link`(원본 엔카 URL)가 쌍끼리 **동일**하다.

| wr_id | 영상 | 사진 | 차량 | sale_link |
|---|---|---|---|---|
| 1038 | **8** | 38 | [BMW] 5시리즈 (2017.03) | …/cars/detail/41937215 |
| 1039 | **0** | 32 | [BMW] 5시리즈 (2017.03) | …/cars/detail/41937215 |
| 1040 | **8** | 40 | [르노삼성] QM6 (2017.05) | …/cars/detail/42364118 |
| 1041 | **0** | 25 | [르노삼성] QM6 (2017.05) | …/cars/detail/42364118 |

wr_id 1006~1041 구간에서 **16쌍 연속** 같은 패턴(1006/1007, 1008/1009, 1010/1011, 1012/1013, 1017/1018, 1019/1020, 1021/1022, 1024/1025, 1026/1027, 1028/1029, 1030/1031, 1032/1033, 1034/1035, 1036/1037, 1038/1039, 1040/1041).

그리고 **교차매칭은 영상 없는 쪽을 잡는다**:

```
GET ?car_no=02다3749&vin=WBAJC3100HG466426
→ "sources":{"inspected":{"matched":1,"wr_id":1039,"videos":[],"photos":[…32장]}}
                          ▲ 1건만          ▲ 사진전용글       ▲ 영상 0

GET ?type=inspected&id=1038          ← 같은 차의 영상글을 직접 찍으면
→ videos 8개 정상
```

즉 **영상은 있다. 매칭 선택이 문제다.**

## 2. board 쪽에 생기는 결과 (왜 급한가)

board 폴러(`board:poll-ssancar-media`, 2분 주기)의 판정은 이렇다:

```php
// SsancarMediaService::pollDecision — 교차매칭(B) 경로만 사용
$inspVideos = count($src['inspected']['videos'] ?? []);
$stockPhotos = count($src['stock']['photos'] ?? []);
'advance' => $inspVideos > 0 || $stockPhotos > 0,
```

- 사진전용글이 잡히면 `inspVideos = 0` → **`advance=false` → 매물이 `현지확인대기(draft)` 에서 영영 안 넘어간다.**
- `has_media` 는 true(사진이 있으니) → 에이지아웃 유예만 받아서 **무한 폴링 상태로 남는다.** 영업은 "검차 끝났는데 왜 전달대기로 안 오지" 상태가 된다.
- 성공하는 경우는 **사진전용글이 붙기 전에 폴링이 도는 차뿐** — 사실상 레이스다. 스캔 당시 짝이 아직 없던 wr_id 1000~1005 만 정상 전이됐다.

현재 heymanboard 운영 매물이 6건뿐이라 표면화가 안 됐을 뿐, **본격 가동하면 자동전이가 거의 안 도는 상태**다.

## 3. 요청 — 교차매칭(B) 응답을 **합산**으로

`?vin=&car_no=` 교차매칭에서 **매칭된 검차(inspected) 글이 여러 건이면 전부 합산**해서 돌려달라.

```jsonc
"sources": {
  "inspected": {
    "matched": 2,                    // ← 매칭된 글 수 (현재는 항상 1)
    "wr_ids": [1038, 1039],          // ← (선택) 어느 글들이 합쳐졌는지. 진단에 유용
    "wr_id": 1038,                   // ← 기존 키는 대표 1건으로 유지(하위호환)
    "videos": [ …두 글의 영상 전부… ],
    "photos": [ …두 글의 사진 전부, 중복 URL 제거… ]
  }
}
```

- **최상위 `videos[]` / `photos[]` 도 같은 기준으로 합산**(board 바이어페이지가 이 둘을 직접 쓴다).
- **스키마는 그대로**(키 이름·타입 불변) — board 는 코드 수정 없이 그대로 동작한다. `matched`/`wr_ids` 는 추가돼도 무시된다.
- **직접모드(`?type=inspected&id=`)는 지금 그대로** 두면 된다. 단일 글 조회가 맞다.
- ⚠️ **`photos` 중복 — URL dedupe 는 소용없다(실측)**: wr_id 1038/1039 의 사진 URL 교집합이 **0장**(38 + 32 = 합집합 70)이다. 파일이 전부 다르다. 따라서 두 글의 사진이 **서로 다른 장면**이면 합산이 정답이고, **같은 장면을 재촬영/재업로드**한 거라면 바이어에게 같은 차 사진이 두 벌 보이게 된다. 어느 쪽인지는 ssancar 만 안다 → §5-2 답변에 따라 갈린다.

**board 단독으로는 못 고친다** — 응답에 1건만 담겨 오므로 board 쪽엔 나머지 글의 존재를 알 방법이 없다. (차선책은 §6.)

## 4. 트래픽 / 리소스 — 실측 기준 (결론: 부담 없음)

**핵심: 이 API 는 사진·영상 파일을 실어보내지 않는다. CDN URL 문자열만 담는다.** 실제 이미지·영상 바이트는 바이어가 볼 때 `cdn.ssancar.com` / `iframe.mediadelivery.net` 에서 직접 나가며, 이 엔드포인트 대역폭과 무관하다.

응답 크기 실측(2026-07-28, 박스에서 `curl -w '%{size_download}'`):

| 호출 | 크기 |
|---|---|
| 교차매칭 현재(사진전용글 1건, 사진 32장) | **8.4 KB** |
| 영상글 1건 직접(영상 8 + 사진 38) | **16.1 KB** |
| 합산 후 예상(두 글) | **≈ 24 KB** (중복제거하면 그 이하) |

→ **콜당 +16 KB 남짓.** 응답시간은 교차매칭 0.19~0.38초, 직접모드 0.05~0.07초로 측정됐다(3회 반복).

호출량은 **전혀 늘지 않는다**(합산은 콜 수가 아니라 응답 내용의 문제):

- board 폴러 = 2분마다 `draft` 매물 수만큼. **응답을 10분 캐시**하므로 실호출은 `draft 수 / 10분` 으로 수렴.
- 현재 운영 draft 2건 → **시간당 12콜 수준**. 합산으로 늘어나는 총 전송량은 **시간당 200 KB 미만**.
- draft 가 50건까지 늘어도 시간당 300콜 · 7 MB 수준이다.

ssancar 서버 부담은 **매칭 행이 1 → N(실측 2)** 이 되면서 그 글들의 파일목록 조회가 붙는 정도. 위 실측 응답시간(0.2초대)이면 여유가 있다.

⚠️ **타임아웃 — 이건 board 쪽 숙제이기도 하다(ssancar 책임 아님).** board 클라이언트는 `Http::timeout(4)`(공개 바이어페이지 가용성 우선)이고, **타임아웃 시 빈 배열 → `advance=false` → 조용히 전이 안 함.** 실측 중 콜드로 추정되는 **4.8초**가 한 번 나왔다(재측정은 0.19~0.38초). 즉 §3 이 고쳐져도 **느린 응답 하나로 같은 증상이 재발**할 수 있다. board 쪽에서 폴러(백그라운드, 기다리는 사용자 없음)와 바이어페이지의 타임아웃을 분리하는 게 정공법 — **board 후속 과제로 잡아둔다.** ssancar 쪽엔 "합산 후에도 교차매칭이 지금 수준(0.2초대)을 유지하는지"만 확인 부탁한다.
