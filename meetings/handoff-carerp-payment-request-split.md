## 0. 한 줄 요약

**[입금요청] 하나를 [매입 계약금] / [매입 잔금] 둘로 쪼개고, 각각 금액을 실어 보낸다.
금액은 ERP 회계에 반영하지 않는다(표시 전용).
요청이 들어오면 ERP 가 알림톡을 보내되, 근무시간 밖(평일 17:30 이후·주말·공휴일)에는 대표에게만 간다.**

## 1. 왜 필요한가 (Jin 2026-08-11)

지금 [입금요청]은 "이 차 입금해주세요" 한 마디뿐이다. 받는 사람이 **얼마를 보내야 하는지 모른다.**
실무에서 금액은 두 번 나간다 — **계약금** 먼저, 나중에 **매입잔금**(계약금 뺀 나머지).
받는 사람은 *"이게 계약금인지 잔금인지"* 를 알아야 처리할 수 있다.

> Jin: "얼마를 보내줘야 하는지 정해서 알려줘야 한다고 하더라고. 그게 계약금인지, 매입잔금인지 알아야 넣어 줄 수 있다고."

**ERP 자동기입은 필요 없다.** Jin 명시: *"ERP에서는 그 금액이 바로 기입되지 않아도돼. 지금처럼 단순 신호체계여도돼.
자동 기입되는건 은행 API 연결된 이후가 되어도 되니까."*
⇒ §11-5 **흡수 금지**(`final_payments`·`purchase_balance_payments` 에 간접적으로라도 쓰기 금지)는 **그대로 유효**하다.

## 2. 🚨 이걸 먼저 읽어야 한다 — 지금 구조로는 물리적으로 불가능하다

`subtype` 같은 하위구분 필드를 얹는 방식은 **작동하지 않는다.** 두 가지가 정면으로 막는다.

1. **멱등키가 `(vehicle_id, type)`** — `open` 인 게 있으면 새 요청을 `already_open` 으로 **조용히 버린다**.
2. **`purchase_payment` 의 소멸 조건이 "매입 미지급 0"** (§11-1 표).

⇒ 계약금을 실제로 지급해도 **잔금이 남았으니 미지급 > 0** → **계약금 요청이 안 닫힌다**
→ 그 차에 잔금요청을 내면 `(vehicle_id, purchase_payment)` 가 아직 open 이라 **skip 된다.**
영업 화면에는 "이미 요청됨" 만 뜨고, 잔금 요청은 **아무 데도 도착하지 않는다.**

**⇒ 반드시 별개 `type` 2개여야 하고, 각 type 의 소멸 조건을 따로 정의해야 한다.** (아래 §3)

## 3. ERP 요청사항 ①  — type 2개 + 소멸 조건

| 신호 | `type` | 단위 | 뜻 | 닫히는 방법 |
|---|---|---|---|---|
| **매입 계약금** | `purchase_deposit` | 차량 1대 | "이 차 계약금 N원 보내주세요" | ⚠️ **수동 확인만** (아래 사유) |
| **매입 잔금** | `purchase_balance` | 차량 1대 | "이 차 잔금 N원 보내주세요" | 기존대로 **매입 미지급 0 이면 자동소멸** + 수동 확인도 허용 |
| ~~입금요청~~ | `purchase_payment` | — | **deprecated** | 신규 생성 없음. **기존 open 행은 그대로 두고 기존 규칙으로 닫는다** |

- ⚠️ **`purchase_deposit` 을 "미지급 0" 으로 자동소멸시키지 말 것.**
  미지급 0 = 잔금까지 다 준 상태다. 그때까지 계약금 신호가 살아 있으면 **"계약금 아직 안 보냈다"는 거짓 신호**가
  차 인수 시점까지 화면에 남는다. 계약금은 ERP 가 알 방법이 없다(금액을 회계에 안 쓰기로 했으므로).
  ⇒ **`sale_payment_confirm` 의 수동 확인 액션을 그대로 재사용**하는 게 유일하게 성립하는 설계다.
  확인 주체도 동일 = `canConfirmFinance()`(super·admin·업무관리자·role∈{재무,관리}).
- **멱등키는 `(vehicle_id, type)` 그대로 둔다.** type 이 갈리므로 계약금이 open 인 동안에도 잔금 요청이 통과한다.
  순서 강제(계약금 확인 전 잔금 금지)는 **넣지 말 것** — 단순 신호라는 성격을 깨고, 실무에서 순서가 뒤집히는 씬이 있다.
- `purchase_deposit`·`purchase_balance` 도 **차량 1대 단위** = 응답 `batch_id` 는 **`null`**(기존 `purchase_payment` 와 동일).
  취소는 기존대로 `GET /requests` 로 `batch_id` 를 먼저 조회.
- **`GET /requests` 응답의 `type` 값에 새 두 개가 그대로 실려야 한다** — board 칩이 type 으로 분기한다.

## 4. ERP 요청사항 ② — 금액 (표시 전용)

- `POST /requests` body 에 **`amount_krw`**(정수, KRW, 선택) 추가.
  - `purchase_deposit`·`purchase_balance` 에서는 **필수**로 봐도 된다(board 가 비면 전송을 막는다).
  - `sale_payment_confirm` 에는 **넣지 않는다** — Jin 확정: *"판매대금확인은 금액칸 불필요, 입금요청만 분리."*
- 저장 = `board_requests` 행의 **표시 전용 컬럼**(예: `amount_krw` nullable unsigned bigint).
- 🚫 **회계 컬럼(`final_payments`·`purchase_balance_payments`·`vehicles.*`)에 쓰지 말 것.** §11-5 흡수금지 그대로.
- ERP 요청 화면(관리/재무가 보는 목록)에 **금액과 구분(계약금/잔금)을 표시**해야 한다.
  아무 데도 안 남으면 돈 보낼 사람이 얼마인지 볼 수가 없어 기능 자체가 무의미해진다.
- `GET /requests` 응답에도 `amount_krw` 를 실어 주면 board 칩에 금액을 같이 띄울 수 있다(**선택** — 없어도 board 는 동작).

## 5. ERP 요청사항 ③ — 알림톡 (발송 주체 = ERP)

**board 는 알림톡 코드를 한 줄도 안 짠다.** 세 가지 이유로 ERP 가 보내는 게 맞다(Jin 직감과 일치):

1. **번호를 가진 쪽이 ERP** — 수신자(재무·관리·대표)는 board 사용자가 아니다.
   board `users.role` 은 영업/현지확인/경매/관리뿐이고 **대표 계정이 없다.**
2. **트리거가 하나여야 한다** — 요청 행 생성 = 발송. board 가 보내면
   **"요청은 `already_open` 으로 skip 됐는데 알림톡은 갔다"** 가 실제로 발생한다.
3. **board 알림톡 채널은 지금 막혀 있다** — BizM 1차 반려 후 재검수 대기(2프로필×2템플릿=4건), 실발송 0.
   여기에 또 얹으면 이미 막힌 채널에 신규 기능이 종속된다.

### 5-1. 수신자 라우팅 — 시간·요일 규칙 테이블 (Jin 확정)

> Jin: *"평시엔 알림톡이 없지만 지정한 담당자 1~2명은 알림톡을 받는거지.
> 그 알림톡은 시간대를 지정할 수 있거나 요일을 지정할 수 있고.. 하이브리드적인?"*

**특수 케이스를 코드에 박지 말고 규칙 테이블 하나로 표현할 것.** 그러면 "17:30 이후엔 대표" 가
예외 분기가 아니라 **규칙의 자연스러운 결과**가 된다.

수신자 규칙 행 = `{ 수신자(ERP user 또는 이름+번호), 요일 집합, 시작시각, 종료시각, 공휴일 포함 여부, 활성 }`

| 예시 행 | 요일 | 시간 | 공휴일 |
|---|---|---|---|
| 담당자 A(통장 보는 사람) | 월~금 | 09:00–17:30 | 미포함 |
| 대표 | 월~금 | 17:30–09:00 (자정 넘김) | — |
| 대표 | 토·일 | 종일 | 포함 |

- 발송 시 **현재 시각(KST)에 매칭되는 모든 행의 수신자**에게 보낸다.
- **종료 < 시작 = 자정 넘김**으로 해석(17:30–09:00). 두 행으로 쪼개는 것보다 설정 실수가 적다.
- ⚠️ **매칭 0명 방지 fallback 필수** — 아무도 안 걸리면 지정 fallback(대표)에게 강제 발송.
  알림톡이 **조용히 0명에게 가는 게 최악**이다(카톡보다 나빠진다).
- **공휴일 = 주말과 동일 취급**(Jin 확정). 공휴일 판정 소스가 ERP 에 있는지 확인 필요 —
  없으면 **설정에 공휴일 수기 등록** 정도로 충분하다(연 1회 입력). 외부 API 끌어오지 말 것.
- 시각 판정은 **서버시각 단일 판정**(board TimeGate 와 같은 원칙). ⚠️ **board 가 미리 판정해서 힌트를 실어 보내지 않는다** —
  판정 지점이 둘로 갈리는 순간 반드시 어긋난다.

### 5-2. 발송 규칙

- ⚠️ **`created` 라인에만 발송한다.** `skipped`(already_open / forbidden)에는 **발송 금지** — 중복 카톡의 원인.
- 1차는 **요청 1건 = 알림톡 1건**(즉시)로 단순하게. 시끄러우면 나중에 N분 배치로 묶는다(지금 선점하지 말 것).
- `sale_payment_confirm` 도 같은 라우팅을 탄다(Jin: *"board에서 요청하는 입금요청 / 잔금확인요청은"* — 둘 다).

### 5-3. 템플릿 본문 — 아이템 리스트 변수 (Jin 확정)

> Jin: *"리스트나 아이템리스트화해서 그 변수안에 계좌정보를 넣을 수 있게 꾸미자."*

가변 목록은 **한 변수에 개행으로 담는다**(car-erp 담당자실적 패턴 그대로).

```
[사내 업무용] 매입 입금요청 #{건수}건

담당자님, 업무 시스템(board)에서 입금요청이 접수되었습니다.

#{요청내역}

ERP 매입 화면에서 확인 후 처리해 주세요.
```

`#{요청내역}` 예시(개행 포함 한 덩어리):
```
■ 매입 계약금 · 12가3456
  3,000,000원
  국민 123456-78-901234 (홍길동)
```

- ✅ **계좌는 ERP 가 이미 갖고 있다** — 연동 B(`purchase_sync`)가 `payee_*` → `purchase_seller_*`,
  `selling_fee_payee_*` → `purchase_fee_*` 로 이미 넣어뒀다. **board 가 계좌를 다시 실어 보낼 필요 없다.**
  ⇒ 요청 payload 에 PII 를 새로 추가하지 않는다(노출면 불변). ERP 가 자기 DB 값으로 본문을 만든다.
- ⚠️ **계좌가 비어 있는 차**가 있을 수 있다(nullable). 그 줄은 **빼고 보내되, "계좌 미등록" 을 명시**할 것 —
  빈 줄로 두면 받는 사람이 계좌를 못 찾고 다시 카톡을 하게 된다(기능의 목적이 무너진다).
- ⚠️ **BizM 템플릿 등록은 인스턴스별로 각각**이다(3사 = 발신프로필 별도). 코드 body 는 하나지만
  **승인은 프로필 수만큼** 받아야 한다. heyman 만 승인받고 배포하면 나머지는 발송 실패한다
  (board 알림톡 2종에서 실제로 겪은 함정 — board `CLAUDE.md` 「남은 작업」 참조).
- ⚠️ 승인 문구와 코드 `body` 가 **한 글자라도 다르면 발송 실패**한다.

## 6. board 측 작업 (참고 — board 세션에서 구현·커밋. 여기서 건드리지 말 것)

1. `CarErpReadService::sendBoardRequest(type, vehicleIds, buyerId?, note?, amountKrw?)` — `amount_krw` 추가.
   HMAC canonical **바이트 단위 일치**(POST 는 raw body 포함).
2. `/portal` 재고 탭(지급대기) 행 = [입금요청] 1버튼 → **금액 입력칸 + [계약금] [잔금] 2버튼**.
3. 칩을 **type 별 2개**로(한 차에 「계약금 확인됨」 + 「잔금 요청중」이 동시에 성립한다).
   `chipMap` 은 이미 type 으로 키잉돼 있어 구조 변경은 없다.
4. 금액 **자동계산 금지**(잔금 = 매입가 − 계약금 자동채움 ❌).
   Jin: *"그건 우리가 알 수 없으니 그것도 기입할 수 있어야"* — §14-5 셀프검차 금액과 같은 원칙.
5. `lang/ko` + `lang/en` **양쪽**.
6. 회귀테스트 `test_board_request_payload_carries_no_amount` 를 **"회계 반영 안 함"을 지키는 테스트로 재작성** + SKILLS §14-2 개정.

## 7. 배포 순서 (⚠️ 어기면 조용히 실패)

**ERP 먼저 배포 → board 나중.** board 가 새 type 을 먼저 보내면 ERP 가 `422` 로 튕긴다.
반대 순서(ERP 먼저)는 무해하다 — 아무도 새 type 을 안 보낼 뿐이다.
알림톡은 **BizM 승인 후 enabled on** 이므로 코드 배포와 실발송 시점이 갈린다(배포 ≠ 작동).

## 8. ERP 쪽에서 판단해 줄 것 (board 는 모른다)

1. `board_requests` 스키마 변경(컬럼 2개: type enum 확장 + `amount_krw`)의 마이그레이션 영향.
2. 기존 `purchase_payment` open 행의 처리 — **그대로 두고 소멸시키는 쪽**을 제안하지만 ERP 판단.
3. 수신자 규칙 테이블을 **새 테이블**로 둘지 기존 설정(JSON)으로 둘지.
4. 공휴일 판정 소스 유무.
5. 알림톡 발송 실패 시 로깅·재시도 정책(board 는 fire-and-forget + 로그만 남기는 방식을 쓴다).
