# 매입 락 승인 요청 — board 판 (주말 2026-11-21~22 작업, 착수 전)

> 정본(양쪽 공통 결정) = car-erp `docs/design/board-purchase-lock-approval.md` · 결정 로그 = car-erp `docs/integration/board-collab.md` §3 2026-11-19.
> 이 문서 = board 가 만들 것만. 🚫 Jin 「시작」 전에는 코드 착수 금지. ERP 가 엔드포인트 스펙 문서를 먼저 낸다 — 그걸 받고 시작.

## 1. 왜

- ERP 는 바이어 입금율이 기준에 못 미치면 매입 등록을 막는다(매입 등록 락). board 는 그 판정(`purchase_locked`)을 그대로 받아 /auction 드로어에서 🔒 바이어의 구매확정을 막는다.
- board 를 쓰기 전에는 ERP 차량 저장 창에서 관리 이상이 사유를 적고 그 저장 1회를 통과시켰다. 지금은 board 가 매입 입구라 그 길이 없다 — 락 걸린 바이어는 그냥 막힌다.
- → board 에서 요청을 보내고 ERP 승인큐에서 관리 이상이 승인/거절한다.

## 2. Jin 확정(2026-11-19, car-erp 세션에서 결정)

| 항목 | 결정 |
|---|---|
| 흐름 | 선승인 — board 요청 → ERP 승인 → board 구매확정 → 평소대로 purchase-sync |
| 승인자 | ERP 관리 이상 전원 중 먼저 본 사람(본인 요청은 본인 승인 불가) |
| 범위 | 차 1대 + 그 바이어, 1회. 키 = `(purchase_listing_id, buyer_id)` |
| 유효기간 | 승인 후 7일 |
| 무효 | 바이어 변경 · 차 삭제 후 재등록(새 listing id) · 7일 경과 — 이 셋뿐 |
| 금액 | **승인 대상 아님** — 「그 바이어의 락을 1회 풀 것이냐」만 판단 |
| 요청 payload | purchase_listing_id · vehicle_number · 차명 · buyer_id · salesman_email(등록 영업) · requested_by_name(누른 사람) · 사유. 차값·판매가·환율·첨부·입금율 스냅샷은 **안 보낸다**(ERP 가 승인 시점에 미수를 다시 계산) |
| 요청 버튼 | 등록 영업 본인 + 관리 대리(누른 사람 이름 기록) |

| 알림 | 알림톡 없음. ERP 벨 「승인 대기」 고정 구역. board 는 **폴링**으로 결과 표시(ERP→board 웹훅 없음) |

## 3. board 가 만들 것

1. **ERP 호출 2개**(`CarErpReadService`, 기존 읽기 HMAC 틀 · POST 는 `logWrite` 전송 표에 남는다) — 요청 생성 POST, 상태 조회 GET `?purchase_listing_id=`. 경로·필드명은 ERP 스펙 문서대로.
2. **/auction 드로어**(`resources/views/livewire/auction/index.blade.php`)
   - 🔒 바이어를 고르면 지금의 차단 문구(`auction.err_buyer_purchase_locked`) 자리에 사유 칸 + [ERP 승인 요청].
   - 드로어 값 선저장 없음 — 바이어 선택 + 사유만으로 요청(금액 필수 검사 안 탄다).
   - 상태 칩: 요청중 / 승인(만료일) / 거절(사유) — §11 요청 칩과 같은 꼴. 거절이면 사유 다시 적어 재요청.
   - 누를 수 있는 사람 = 등록 영업 본인 + 관리 대리(포털 대리 규칙과 같은 판정을 쓸지 = 착수 때 확인).
3. **구매확정 통과 조건**(`conclude()` :922 부근) — 락 바이어여도 그 `(listing, buyer)` 승인이 **유효·미사용**이면 통과. 저장 직전 ERP 에 다시 묻는다(지금 `buyerLockedNow()` 가 하는 자리). 화면 버튼 비활성 판정(`purchaseBlockReason()`)도 같은 조건.
4. **결과 알림** — 상단 종(`notify/bell`)·웹푸시 명령(매분 `board:push-request-results`)에 승인/거절 결과를 얹는다(§11 결과와 같은 자리).
5. **감사 행** — 요청 보냄(누가·대리 명의·차량·바이어·사유·결과) 1행(Jin 「board 모든 건 로그」).
6. **purchase-sync** — 승인 id 필드를 실을지는 ERP 가 착수 때 알림. ERP 는 그 purchase_listing_id 로 들어오면 승인을 소진 처리(수신부가 락을 새로 검사하지는 않는다).
7. **문구** ko·en 양쪽 · 테스트(`BoardTest`/새 파일: 락+승인 없음 = 차단 / 승인 유효 = 통과 / 다른 바이어 = 차단 / 만료·사용됨 = 차단 / 거절 = 사유 표시·재요청).
8. **가이드** — 「경매/구매」 가이드에 단계 추가(Jin 로컬 확인 뒤).

## 4. 건드리지 않는 것

- 상태머신·연동 B 발사 시점(won 1회) · 재고매입(바이어 미정 — 락 검사 대상 아님) · 락 판정 조건(ERP `purchase_locked` 그대로 신뢰, board 재계산 금지).

## 5. 주의

- 승인 대기 동안 그 차는 `accepted` 에 멈춰 있다(구매확정 불가). 급한 차는 ERP 관리자에게 직접 말해야 한다(알림톡 없음).
- 폴링은 분당 120 공유 한도 안에서 — 드로어 열 때 + 종의 기존 폴링 주기에 얹고, 따로 짧은 주기 폴링을 만들지 않는다.
- 조회 실패(ERP 무응답)는 「승인 없음」으로 본다(막는 쪽이 안전).

## 6. 순서(주말)

ERP 스펙 문서 수신 → 3-1 호출 → 3-2·3-3 화면·통과 조건 → 로컬 e2e(board ↔ 로컬 ERP: 요청 → ERP 승인큐 승인 → 구매확정 → sync, 거절·만료 경로) → 3-4 알림 → Jin 로컬 확인 → 가이드 → 배포(Jin 직접 지시, ERP 먼저/board 먼저 순서는 그때 car-erp 세션과 확인).
