## 1. 무엇을 만들려는가

Jin 요청(2026-09-08): **차값이 쌀 때 바이어 없이 미리 사두는 매입**을 board 에서 정식 경로로 만든다.

- board `/auction` 구매확정 드로어에 **「재고매입 (바이어 미정)」 토글**을 넣는다.
- 켜면 바이어 드롭다운이 비활성 → 연동 B 로 `buyer_id: null` 전송.
- **기대 동작(Jin)**: ERP 에서 그 **영업담당자의 「일반재고」**로 잡히고, 이후는 **ERP 화면에서 그대로 진행**한다.
  ERP 에서 바이어를 지정하면 「선적전」으로 빠지는 기존 흐름을 그대로 탄다. board 는 이후 관여하지 않는다.

## 2. board 현행 — 왜 지금은 안 되는가

- 2026-08-10 부터 board 는 **구매확정 시 바이어 선택을 필수**로 막고 있다(`err_buyer_required`).
  이유 = 연동 B 는 ERP 저장 게이트를 안 타므로 **매입 등록 락(§4-0)의 유일한 상류 차단점이 board 화면**인데,
  바이어를 안 고르면 `buyer_id: null` 로 나가 **락 판정 자체가 성립하지 않는다**(= "안 고르면 통과").
- 즉 지금 없는 건 payload 능력이 아니라 **board 화면의 차단**이다. `buyer_id: null` 은 계약상 이미 허용값이다
  (board §12: "미선택 null", 2026-08-10 이전에는 실제로 null 로 나갔다).

## 3. board 가 보내려는 payload (제안 — **이대로 받아지는지가 질문 2**)

`contract_version: 4` 그대로, 재고매입일 때만 아래가 달라진다. 나머지(vehicle_number·owner_name·source·
salesman_email·payee_*·selling_fee_payee_*·attachments·purchase_price_krw·selling_fee_krw)는 **전부 기존과 동일**.

```json
{
  "buyer_id": null,
  "consignee_id": null,
  "sale_price": null,
  "sale_currency": null,
  "sale_exchange_rate": null,
  "transport_fee": null,
  "final_price": null
}
```

⚠️ **`sale_price: null` 을 명시적으로 보내야 하는 이유** — board Job 은 지금 판매가 칸이 비면
`차량금액(KRW) ÷ 환율` 로 **sale_price 를 자동 파생**한다(`SyncWonListingToCarErp.php`).
그대로 두면 바이어만 없고 **판매가는 차값이 그대로 실려** 나간다. 재고매입은 판매가가 아직 없는 게 정상이므로
board 가 파생을 끄고 null 을 보낼 계획이다. **질문 1의 답에 따라 `null` 이 아니라 `0` 이어야 할 수도 있다.**

## 4. 질문

### Q1. 「일반재고」 판정식 (**가장 중요**)

`erp/inventory` 의 **4분류 판정 술어(predicate)를 코드 기준 그대로** 알려달라 —
`awaiting_payment` / `general` / `pre_ship` / `shipped_out`.

- board 문서에는 「일반재고 = 바이어 없음(`sale_price ≤ 0` = 투기매입)」이라고 적혀 있는데, 이건 **board 의 전사(轉寫)**다.
  판정이 `sale_price` 기준인지 `buyer_id` 기준인지에 따라 board 가 보낼 값이 달라진다(§3 참조).
- 그리고 구체적으로: **`buyer_id = null` + `sale_price` 없음 + 매입대금 미지급** 상태의 신규 차량은
  **어느 분류로 떨어지나?**
  - Jin 기대 = 바로 「일반재고」.
  - board 예상 = 매입 미지급이므로 **「지급대기」에 먼저 잡히고**, 매입대금 지급 후 「일반재고」로 이동.
  - 어느 쪽이 맞는지 알려주면 board 가 Jin 에게 정확히 안내한다(화면에 다르게 보이면 버그로 읽힌다).

### Q2. §3 payload 가 그대로 통과하나 — 422 나는 필드가 있나?

특히:
- **`sale_currency: null`** — 계약 표기가 `"USD|EUR|KRW"` 라, 수신측 검증이 `in:` 만 있고 `nullable` 이 없으면 죽는다.
- `sale_price` 는 **`null` 과 `0` 중 어느 쪽을 원하나?**
- `final_price`(v2 호환 필드) 를 null 로 보내도 되나? (수신측이 `purchase_price_krw ?? final_price` 로 쓰는 걸로 안다)
- `consignee_id: null` 은 당연히 문제 없을 것으로 보지만 같이 확인 부탁.

### Q3. 나중에 바이어를 지정할 때 매입 등록 락이 작동하나 — **위험 고지**

board 는 재고매입 차에 대해 **락 검사를 건너뛸 계획**이다(바이어가 없으니 걸 대상이 없다).
그래서 남는 게이트는 ERP 쪽 하나뿐이다.

> **ERP 화면에서 기존 차량에 바이어를 지정할 때(판매탭 편집), `purchase_locked` 판정이 발동하나?**

- **발동한다** → 재고매입 경로는 안전하다. 락은 지정 시점으로 미뤄질 뿐 사라지지 않는다.
- **발동 안 한다** → 2026-08-10 에 막은 구멍이 **문 하나 옆에서 다시 열린다**:
  락 걸린 바이어라도 "재고매입으로 사두고 → ERP 에서 그 바이어를 붙인다"가 가능해진다.
  이 경우 board 는 구현을 멈추고 Jin 판단을 받는다. **없으면 없다고만 알려주면 된다**(그쪽에서 게이트를 만들어달라는 요청이 아니다).

### Q4. 재고매입을 구분하는 플래그가 필요한가?

`buyer_id: null` 만으로 ERP 가 충분히 구분하나, 아니면 매입탭 표시·감사 목적으로
**`stock_purchase: true`(→ `contract_version: 5`)** 같은 필드를 실어주는 게 나은가?

- board 기본 입장 = **불필요**(양쪽 "모르는 필드 무시" 규칙이라 보내도 무해하지만, 안 쓸 필드를 계약에 넣지 않는다).
- ERP 가 화면에 표시하거나 필터하고 싶다면 넣겠다. **그 경우 §12 규칙대로 car-erp 먼저 배포**다.

### Q5. §11 입금요청 신호 (확인만)

재고매입 차도 매입대금은 지급해야 하므로 board `/portal` 재고 행의 **[계약금]/[매입잔금]** 요청이 그대로 필요하다.
`purchase_deposit` / `purchase_balance` 는 **차량 1대 단위**라 바이어와 무관할 텐데, **바이어 없는 차량에도 정상 동작하나?**
(「판매대금확인」은 바이어 묶음이라 애초에 해당 없음 — 그건 안 쓴다.)
